# 阶段 1：抓包基础

本阶段完成网卡枚举、真实抓包、后台线程与停止、BPF 抓包过滤、统计以及用于验收的 PCAP 写入。
GUI 与协议解析尚未实现，当前命令行输出展示原始包的元数据，不会声称已经识别 HTTP 等协议。
自动验收通过随机标记确认抓到的包确实来自自行产生的流量。

## 运行

在终端进入项目目录（路径带空格，需要引号）：

```bash
cd "/Users/roya/Desktop/security project"
```

环境已在 `.venv` 中准备好。查看网卡：

```bash
.venv/bin/python -m lab1a_sniffer interfaces
```

一键验收回环接口、物理网卡与无流量停止，并保存结果：

```bash
.venv/bin/python -m lab1a_sniffer selfcheck --physical-interface en0 --output-dir artifacts/stage1
```

预期末尾出现 `"passed": true`。其中各项检查也应为 `true`，`error` 应为 `null`。
物理网卡检查需要 `en0` 有可用的 IPv4 网络连接；如果网卡不同，先查看网卡列表，再替换参数。
该检查发送三个带随机标记的 UDP 包到文档地址 `192.0.2.1`，TTL 为 1，并绑定指定物理网卡，
只验证出站捕获，不需要远端服务或回复。回环检查仅连接本机的临时 HTTP/UDP 服务。

手动抓包 10 秒，可以按 Ctrl+C 提前停止：

```bash
.venv/bin/python -m lab1a_sniffer capture -i en0 -f 'tcp or udp' -t 10 -w artifacts/stage1/manual.pcap
```

命令行 PCAP 输出目录须已存在；上述自动验收会创建 `artifacts/stage1`。
`capture` 默认不启用混杂模式，最多读取 20000 个包或约 128 MiB 数据，避免无限增长。
本阶段的限额针对读取量，最后一个包可能使字节计数超过上限，最多超过一个 snaplen。

独立核对 PCAP（无需安装 Wireshark）：

```bash
/usr/sbin/tcpdump -nn -r artifacts/stage1/lo0.pcap
/usr/sbin/tcpdump -nn -r artifacts/stage1/en0.pcap
```

`artifacts/` 已被 Git 忽略，保存的网络数据不会随源码提交。

## 数据流与代码分工

```text
系统网卡 / BPF
    ↓ libpcap 的非阻塞读取
LiveCapture（工作线程拥有原生句柄）
    ↓ 复制原生内存为 bytes
RawPacket（时间戳、原始长度、链路类型、数据）
    ↓ 有界队列
CaptureSession.drain()（目前由 CLI 消费，后续由 GUI 消费）
```

- `src/lab1a_sniffer/_ffi.py`：声明 C 函数参数和返回类型、C 结构体布局。
- `src/lab1a_sniffer/pcap.py`：枚举网卡，配置并激活 libpcap，读取原始包，关闭句柄，写 PCAP。
- `src/lab1a_sniffer/models.py`：定义不依赖原生库或 GUI 的数据对象。
- `src/lab1a_sniffer/capture.py`：拥有抓包线程、有界队列、停止事件、时长/数量/字节数限额和统计。
- `src/lab1a_sniffer/diagnostics.py`：启动本地测试服务，产生标记流量并验证捕获结果。
- `src/lab1a_sniffer/cli.py`：命令行入口、运行状态和错误输出。

## 应当理解的六个问题

### 1. libpcap 和 Python 分别做什么？

libpcap 负责对接系统抓包机制、应用 BPF 过滤、获取原始数据。
Python 的 `ctypes` 将 Python 调用转换为 C ABI 调用；程序负责正确声明参数与内存布局。
当前没有使用 tcpdump 子进程来代替抓包，也没有使用现成协议解析器。
例如 macOS 的 `timeval` 使用 64 位秒字段、32 位微秒字段和自然对齐填充，不能照搬 Linux 的类型。
测试特意把填充字节设为非零，检查微秒值不会错误地把填充读进去。

### 2. 为什么不能把 libpcap 返回的指针直接放进队列？

`pcap_next_ex()` 返回的是 libpcap 管理的内存，下一次读取后可能失效。
必须在读取下一包前复制为 Python `bytes`，后续跨线程传递的才是独立数据。
时间戳也立即复制为秒和微秒两个整数，不长期保存原生结构体引用。

### 3. 为什么要记录链路类型？

本机验证中 `en0` 返回 Ethernet（DLT=1），`lo0` 返回 NULL（DLT=0）。
两者头部不同，下一阶段解析 IP 时起始偏移也不同。不能对所有包统一跳过 14 字节。
还要区分运行平台的 DLT 与 PCAP 文件中的 LINKTYPE 编号，写文件由 libpcap 完成映射。

### 4. 如何在没有新包时停止？

句柄使用非阻塞读取，等待读取就绪的时间最多 50ms；没有可选择描述符时短暂等待停止事件。
每次循环检查停止标志。主线程只设置标志，关闭操作仍在工作线程完成，避免读和关闭同时发生。
每次重新抓包创建新的会话；异常路径和正常路径都通过 `with` 释放句柄。

### 5. 两类丢包计数有什么区别？

- `queue_dropped`：程序读到了包，但有界队列已满，未能交给消费者。
- `kernel.dropped`：libpcap 提供的内核捕获缓冲区丢包计数。
- `kernel.received`：平台定义的接收计数，可能包含被 BPF 筛掉的流量，不能直接当作程序已捕获数量。
- `kernel.interface_dropped`：接口丢包计数，部分平台不支持；返回 0 不等于能证明网络全程无丢包。
- `packets_read`：本程序从 libpcap 实际取出的包数。

本阶段队列最多存储 2048 个包；CLI 定期取出。即使消费者停止取包，内存也不会无限增长。
数量和字节数上限按已读取的包计算，即使队列满也会停止。

### 6. HTTP 标记验收代表什么？

测试脚本发出本地 HTTP 请求，并检查原始包是否包含随机标记。这证明抓到了已知流量，
不代表程序已具备 HTTP 协议识别能力。HTTP 请求行、响应行与字段解析在下一阶段实现。

## 测试与环境重建

默认测试不发送网络测试流量，不打开实时抓包句柄：

```bash
.venv/bin/python -m pytest
```

加入真实抓包验收（包括本地 HTTP/IPv4 UDP/IPv6 UDP、物理网卡、十次空闲启停、非法过滤与资源释放）：

```bash
.venv/bin/python -m pytest --run-live --physical-interface en0
```

依赖通过 `uv.lock` 锁定，环境可用以下命令重建：

```bash
uv sync --frozen --python 3.13
```

当前封装仅支持 64 位 macOS。实时抓包需要当前用户可读写 `/dev/bpf*`；程序不会自动提权、
修改设备权限或安装系统组件。本机权限已检查可用，如果换机器发生权限错误，应先依据具体错误排查。

本项目只需要 Qt Widgets，因此依赖使用 `PySide6-Essentials` 分发包，提供的 Python 导入路径仍为
`PySide6`，包含 QtCore、QtGui、QtWidgets。无需下载 WebEngine 或 Addons。
