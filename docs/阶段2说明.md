# 阶段 2：分层协议解析

第一阶段验证的是“抓到了正确的流量”；第二阶段验证的是“能解释这些字节的含义”。
本阶段完成纯 Python 解析器，并保留命令行验收。GUI 在下一阶段实现。

## 运行与验收

进入项目目录，在现有环境中运行；本阶段没有新增依赖：

```bash
cd "/Users/roya/Documents/ChatGPT/security project"
.venv/bin/python -m lab1a_sniffer selfcheck --analyze --physical-interface en0 --output-dir artifacts/stage2
```

脚本自动生成本地 HTTP 请求/响应、IPv4 UDP、IPv6 UDP、本地 IPv4/IPv6 ping 和物理接口上的出站 UDP。
终端给出检查结果与协议计数，末尾应为 `"passed": true`。重点查看：

- `loopback.checks.http_request_fields`、`http_response_fields`：解析出了请求/响应和正确的端口。
- `udp_ipv4_fields`、`udp_ipv6_fields`：地址族、地址和 UDP 端口符合实际测试服务。
- `http_has_lower_layers`：HTTP 包同时属于 TCP、IPv4。
- `physical.checks.ethernet_ipv4_udp_fields`：正确跳过 Ethernet 头，识别目的地址和端口。
- `icmp.checks.icmp_ipv4_echo`、`icmp_ipv6_echo`：识别本机 ping 产生的两种 ICMP。
- 三组 `analysis.issue_count` 均应为 0；异常输入的提示功能另用固定样本测试。

完整分层字段和字节偏移保存在 `artifacts/stage2/selfcheck.json` 的 `analysis.samples`，
原始包分别保存在 `lo0.pcap`、`en0.pcap` 和 `icmp.pcap`。
`protocol_counts` 按最高解析层计数：HTTP 包在这里归入 HTTP，不重复计入 TCP；显示过滤仍可匹配 TCP。
端口、时间戳和 TCP 包数量会随每次运行变化。

可以用系统 tcpdump 独立查看相同原始包：

```bash
/usr/sbin/tcpdump -nn -S -vv -r artifacts/stage2/lo0.pcap
/usr/sbin/tcpdump -nn -vv -r artifacts/stage2/icmp.pcap
```

## 手动查看字段与原始字节

命令行 `capture` 默认展示协议、源/目的地址、端口和摘要。新增参数：

- `--details`：展示各层字段。
- `--hex`：展示十六进制和 ASCII；每包最多显示 4096 字节，但原始数据仍完整保留。

例如在一个终端抓回环 ICMP：

```bash
.venv/bin/python -m lab1a_sniffer capture -i lo0 -f 'icmp or icmp6' -t 10 --details --hex
```

在另一个终端产生流量：

```bash
ping -c 1 127.0.0.1
ping6 -c 1 ::1
```

应看到 `NULL → IPv4 → ICMP` 和 `NULL → IPv6 → ICMPv6`，包括类型、代码、标识符和序号。
Ctrl+C 可提前停止。BPF 仍是抓包条件，不能将 `http` 直接作为 BPF 关键字；HTTP 显示过滤在 GUI 阶段接入。

## 数据流与类型

```text
RawPacket
  → 链路层：Ethernet / NULL / LOOP / 原始 IP
  → 网络层：IPv4 / IPv6（及支持的扩展头）
  → 传输或控制协议：TCP / UDP / ICMP / ICMPv6
  → 应用层：HTTP/1.x（如果起始格式可以识别）
  → ParsedPacket：协议层、字段、地址、端口、摘要、解析提示
```

- `src/lab1a_sniffer/parser.py`：纯解析逻辑，不访问网卡，不依赖 Qt，也不调用现成协议解析库。
- `models.py` 中的 `PacketField`：字段名称、显示值、原始包中的偏移和长度。
- `ProtocolLayer`：层名、头部范围、字段列表。
- `ParseIssue`：问题类型、中文说明和发生位置。
- `ParsedPacket`：保留原始包引用，集中提供地址、端口、各层、摘要和提示。
- `src/lab1a_sniffer/formatting.py`：将解析结果转换为可读文字或 JSON。

字段范围均相对 `RawPacket.data`，后续 GUI 可直接使用这些范围关联十六进制视图。
`matches_protocol("TCP")` 沿所有已解析层查找，而非仅比较最后一层。

## 五个核心原理

### 1. 先确定从哪里开始解析

Ethernet 基本头为 14 字节；macOS 的 NULL 回环头是 4 字节，地址族使用本机字节序；
LOOP 头的地址族使用网络字节序。原始 IP 没有上述链路头，直接读取 IP 版本。
解析器还可跳过 VLAN 标签，并限制最大嵌套层数。

### 2. 不假设所有头部都是固定长度

IPv4 头部长度为 IHL 的低 4 位乘以 4；TCP 头部长度由 Data Offset 的高 4 位乘以 4 得到。
两者都可能包含选项，因此不能总是用 20 字节定位下一层。
程序显示选项的原始字节，当前不解释每一种选项语义。

### 3. 可用长度和协议声明长度必须分别检查

捕获数据可能因 snaplen 被截断，协议字段也可能畸形。
程序同时检查已捕获的字节数和 IP 声明的长度：前者不够时标记截断，后者自相矛盾时标记畸形。
Ethernet 帧尾可能有填充，IP 总长度外的内容不送给 TCP 或 HTTP 解析。

### 4. “这是 TCP”与“这是 HTTP”需要不同证据

IP 协议号 6 指示 TCP；解析完整 TCP 头部后，才能定位其载荷。
HTTP 则根据载荷起始位置的请求行或状态行识别，不以 80/443/8080 端口作为判据。
例如 `GET /lab1a HTTP/1.1` 可以在非标准端口识别，80 端口上的 TLS 字节也不会因此被标为 HTTP。

仅当起始行格式可确认时加入 HTTP 层；起始行或头字段跨包时，呈现可确认部分并提示不完整。
本程序按单个 TCP 载荷识别，没有连接上下文，因此可能漏掉跨段内容，也不是完整的 HTTP 合规验证器。

### 5. 不能解析时，说明原因并保留已知信息

`issues` 区分：

| 类型 | 含义 |
| --- | --- |
| truncated | 已捕获数据不完整 |
| malformed | 版本、长度或字段格式不合法 |
| fragmented | 遇到需要重组的 IP 分片 |
| incomplete | HTTP 起始行或头部尚不可完整解释 |
| unsupported | 链路类型、协议或扩展头未实现 |
| encrypted | 遇到 ESP 等不解密的内容 |
| limit | 达到扩展头嵌套或 HTTP 头部解析上限 |

例如 IPv4 分片即使是首片，也不直接声称完整识别出了 TCP/HTTP。
IPv6 的 Hop-by-Hop、Routing、Destination 扩展头按长度跳过；真正的分片停止上层解析，
不需要重组的原子分片可继续。扩展头最多 8 层，HTTP 头部最多解析 16 KiB、128 个字段，限制对象数量与内存开销。

## 测试与当前边界

完整测试（含真实网卡）命令：

```bash
.venv/bin/python -m pytest --run-live --physical-interface en0
```

固定样本位于 `tests/packet_samples.py`，从字段独立构造，不调用生产解析器生成预期结果。
测试同时覆盖请求/响应、重复 HTTP 字段、HTTP 不完整、非标准端口、VLAN、可变头部、IP 分片、
IPv6 扩展头、错误长度、截断后的字段范围，以及 1500 组确定性随机输入。
另将五种参考报文写入 PCAP，用系统 tcpdump 交叉核对地址、端口、序列号、TTL/跳数和 ICMP 字段。
同一组人工构造的独立报文也提供为 `samples/protocols.pcap`，可用于后续离线浏览验收，
它们不是完整 TCP 会话；真实捕获文件仍单独存于 `artifacts/`。

本阶段不做 IP 分片/TCP 流重组、HTTP 消息体还原、chunked/gzip 解码、HTTPS 解密、进程关联，
也不验证报文校验和。校验和只展示数值，避免将系统 offload 造成的中间状态误判为损坏。
IPv6 巨帧、AH 及未实现协议会明确提示。GUI、离线文件打开与交互式过滤在后续阶段完成。
